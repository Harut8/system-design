The full five-call-class workload, with the defence stack as a list you can reorder. Each pattern wraps the ones below it, so order is semantics — a retry above the quota gate re-reserves tokens on every attempt. Come here after the ten steps.

Read this before comparing numbers with the Learn tab
Here the unit is a user turn, not a request. One turn fans out to 3.11 LLM calls — a safety classifier, usually a query rewrite, an answer, sometimes a thinking escalation, sometimes a title. So 10 turns/sec for 10s is 100 turns but about 311 calls, spread over three model tiers. A provider incident hits one tier (Sonnet by default), so an error rate applies only to the answer class — roughly a third of the calls. If you want arithmetic you can check request-by-request, use the Learn tab.
About

What this is

A browser companion to the Python lab in this folder. The Learn tab is ten small experiments — one call class, one provider, one fault at a time — where you watch individual requests rather than aggregate charts. That is the only way a retry becomes legible: you can see the second attempt and the gap before it.

The Sandbox tab is the full thing: five call classes across three model tiers, three token meters, and a reorderable stack.

Honesty

Every number in the fixture is invented. The provider model is a plausible shape, not a model of anyone's infrastructure. This simulates mechanisms. Nothing here is a measurement of any provider and none of it should be quoted as one. Runs are seeded and deterministic, so when you change one knob the difference you see is caused by that knob.

Not modelled: token-level streaming, prompt caching's effect on rate-limit accounting, multi-region failover, and anything at all about answer quality. This measures whether you got an answer, never whether it was a good one.

Prior art, and what doesn't exist

I could not find a public interactive simulator that lets you compose and reorder resilience patterns and watch the cascade, which is why this exists. Adjacent things that do:

  • SimPy — the Python discrete-event framework this kernel is a miniature of.
  • Netflix concurrency-limits — the gradient algorithm implemented for real.
  • Resilience4j — the clearest written spec of these state machines.
  • Envoy adaptive concurrency — where adaptive limits and retry budgets belong for most services.
  • AWS Builders' Library on jitter — the origin of the full-jitter formula in step 6.
  • Google SRE Book: Handling Overload — the criticality ladder behind step 10.
  • Marc Brooker's blog — the best writing anywhere on retries, timeouts and queueing.
  • Chaos tools (Gremlin, Chaos Mesh, Litmus) tell you what your system does; this tells you what the pattern does.

Links were correct at the time of writing; I have no network access from here, so verify before relying on any of them.
